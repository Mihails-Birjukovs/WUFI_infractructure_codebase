# Architecture and data flow

The infrastructure is divided by implementation language, not by scientific wall type. The Mathematica workflow produces the primary model/sensor comparison products. Python provides upstream climate preparation and downstream diagnostics **as well as a distinct WUFI-facing batch/ASC/optimisation workflow introduced in October 2026**.

~~~

## Separate Python WUFI workflow introduced 20 October 2026

~~~text
source .w6p ──> Python batch launcher ──> operator-reviewed .bat
                                         |
                                licensed Windows WUFI
                                         |
                                       .ASC
                                         |
                            Python ASC post-processor ──> CSV / JPG

source .w6p ──> Python construction parameter sweep or thickness search
                ──> generated candidate project copies
                ──> licensed Windows WUFI ──> .ASC summaries and rankings
~~~

The [batch launcher](https://github.com/Mihails-Birjukovs/WUFI_infractructure_codebase/blob/WUFI_python_tools/python_tools/WUFI_Batch_Launcher_Automated_v1.0/README.md) does **not** execute WUFI itself; the [construction scripts](https://github.com/Mihails-Birjukovs/WUFI_infractructure_codebase/blob/WUFI_python_tools/python_tools/WUFI_Wall_Construction_Optimisation/README.md) **do**. The [Python post-processor](https://github.com/Mihails-Birjukovs/WUFI_infractructure_codebase/blob/WUFI_python_tools/python_tools/WUFI_Data_Post_Processor_Automated_v1.0/README.md) exports CSV/JPG files rather than the five WXF datasets of the Mathematica workflow.

These paths must **not** be described as identical: Python launcher does not produce the Mathematica manifest; ASC/case matching can be positional; overwrite, thermal-property, numerical-parity and Windows acceptance questions remain open. [Issues #28–#35](https://github.com/Mihails-Birjukovs/WUFI_infractructure_codebase/issues) are awaiting collaborator review.

## Contracts and boundaries

The WUFI project and model settings are **inputs**, not generated by the Python diagnostics. The launcher builds a project/case manifest, which the post-processor uses to locate ASC files and produce outputs. The comparison tool requires actual sensor identification, a canonical registry and matching time coordinates. All sensor-to-wall interpretations remain subject to installation records.

Post-processing produces five per-case WXF categories: **temperature, relative humidity, dew point, layer water content, total water content**. Plot counts depend on graphics mode; image quantities should not be confused with the number of scientific channels.

The original Python multiscale/DMD modules operate on **already aligned** data; they are conceptually separate from the newly contributed WUFI-facing Python scripts. The original Phase-4 Butterworth methodology differs from the report's centered-mean reconstruction; consult [modal methods](modal.md).

## Time representation

The REF/HEMP historical WAC reproducibility path uses a **fixed UTC+2 WUFI wall-clock convention**, not daylight-saving Europe/Riga transitions. Sensor timestamps are UTC-normalized before comparison; end-of-hour labels and units must remain explicit.

## Source-of-truth hierarchy

1. Approved original data and installed physical system for observational facts.
2. Frozen WUFI project files for simulated physics and boundary conditions.
3. Tool source at recorded commit for implemented algorithms.
4. Original archived manifests and test reports for historical execution evidence.
5. Public site as a **curated explanatory snapshot**, not as independent primary evidence.

The site links to both branch-specific source trees rather than joining them.
